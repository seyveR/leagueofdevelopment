# API версии 0.2.1

Встроенная схема: /api/docs, OpenAPI /api/openapi.json. JSON-запросы и ответы валидируются Pydantic. Ошибки не возвращают SQL, пароли или токены сессии.

Перед изменяющими запросами получите GET /api/auth/session. Ответ содержит user (либо null) и csrf; браузер сохранит HttpOnly-cookie. Передавайте csrf в X-CSRF-Token, cookie — автоматически same-origin. POST/PUT защищены сравнением CSRF и проверкой Origin. Запросы без cookie-сессии не получают данные родителя или администратора.

Новые отчёты доступны только admin (parent — 403, без сессии — 401). Списки возвращают items, total, offset, limit (1–100, по умолчанию 20). Переходы дополнительно возвращают total_openings, total — число кружков с переходами. В деталях прохождения сохраняются исторический снимок ребёнка, результат и версия набора; правильные ответы не добавляются в родительские API. Незавершённое или отсутствующее прохождение — 404. Миграция схемы для отчётов не требуется.

400 — неверный текущий пароль или новый совпадает с текущим; 401 — нужен вход; 403 — роль или CSRF; 404 — сущность не найдена или не принадлежит родителю; 409 — конфликт/незавершённый тест/изменение сохранённого ответа; 422 — неверные поля; 429 — лимит попыток; 503 — ошибка БД. Клиент сохраняет выбор при неуспехе запроса и допускает повтор.

Смена пароля доступна parent/admin только для себя, без параметра email/id. Новый пароль и подтверждение — 10–128 символов, пробелы не обрезаются. Обновление Argon2id-хеша и удаление сессий выполняются одной транзакцией. При ошибке commit остаются прежние пароль и сессии. Лимит смены — 5 попыток на учётную запись за 15 минут плюс общий IP-лимит. Успех удаляет обе cookie; следующий вход сначала получает новый CSRF. Клиент обрабатывает 401 защищённых запросов централизованно, исключая ожидаемые ошибки входа. Поздний 401 от предыдущей сессии не завершает новый вход.

completed считается один раз при атомарном завершении сессии. club_open — отдельное открытие карточки из рекомендаций через кнопку, до перехода на карточку. Точный повтор одного request_id учитывается один раз. Новое осознанное открытие после возврата может создать новое событие. Обычный просмотр каталога, звонок и запись этими счётчиками не считаются.

Вход ограничивает только последовательные ошибки для нормализованного email: первые 14 возвращают 401, пятнадцатая — 429 и Retry-After: 60. В течение следующих 60 секунд неверные запросы возвращают 429 с оставшимся временем, не продлевая паузу. После неё новый неверный вход считается первым. Правильный пароль всегда разрешён, даже во время паузы; счётчик сбрасывается в транзакции создания сессии. Ограничений по числу успешных входов или общему IP для входа нет. Несуществующий email обрабатывается тем же способом. Состояние хранится в login_buckets с отдельным пространством ключей login-failures-v2; старые счётчики не блокируют вход после обновления. Регистрация и смена пароля используют отдельную прежнюю политику.


Создание ребёнка и кружка принимает необязательный UUID request_id. Frontend использует устойчивое значение для повторов одной операции; такой повтор возвращает запись с тем же id. Ответы ошибок валидации не включают input и пароль.
